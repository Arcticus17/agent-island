# Agent Island 正确性与灵活前端设计

日期：2026-09-04  
状态：待用户审阅

## 1. 背景

Agent Island 1.8.2 是一个面向 Windows 的 Tauri 2 桌面应用。Rust 后端负责发现 Claude Code、Codex CLI、OpenCode 和 Hermes 进程，读取本地会话日志，计算状态与用量，并提供进程和终端控制；原生 JavaScript/CSS 前端负责灵动岛、通知、审批、总览和设置界面。

当前已确认两类正确性问题：

1. 灵动岛可能显示用户当前任务中不存在的历史对话或其他项目会话。
2. 成功、失败和等待状态可能误判、持续显示错误，或完全不显示。

代码调查显示，Claude/Codex 会话目前按全局最近修改时间选取最多三个日志文件，没有与正在运行的进程、项目或终端建立可靠绑定。Agent 总状态又取自该列表的第一份日志，因此旧会话和旧错误可能污染当前任务。现有测试覆盖布局辅助函数、用量解析、危险命令分类和 Hook 设置合并，但没有覆盖会话归属、事件顺序、状态转换和前端一致性。

## 2. 目标

本轮工作按以下优先级推进：

1. 功能正确：不显示错误归属的对话，不用历史错误代表当前任务。
2. 可验证：关键状态和会话规则由自动化测试证明。
3. 前端协调灵活：实时更新、交互、动画和可配置布局互不干扰。
4. 前端美观：采用自适应模块岛布局和石墨玻璃视觉体系。
5. 技术可替换：Tauri、Rust、Svelte 和 Windows 平台能力通过稳定边界解耦。

## 3. 非目标

本轮不实现 macOS 或 Linux 版本，不拆出独立后台服务，不建立云端账号或同步服务，也不同时替换 Tauri/Rust。只有在模块边界建立后，现有技术被验证为真实阻碍时，才考虑进一步替换。

## 4. 产品规则

### 4.1 活动与历史会话

- 灵动岛只展示与当前运行进程可靠匹配的活动会话。
- 历史会话只出现在会话总览中，并标注生命周期和最后活动时间。
- 无法唯一确定归属时显示“无法确认当前会话”，不得随机选择最近日志。
- 进程启动前产生的日志不得成为当前活动会话的依据。
- 会话切换后，状态、日志、目录和当前文件必须来自同一个 `session_id`。

### 4.2 日志语义

- 日志按事件时间正序呈现。
- 用户消息、Agent 回复、工具调用和工具结果使用不同记录类型。
- 工具输出不得伪装为 Agent 对话。
- 前端只展示已标准化记录，不直接解释 Agent 原始日志。

## 5. 状态模型

状态拆为三个正交维度：

```text
ProcessState: stopped | running
TurnState: idle | executing | succeeded | failed
AttentionState: none | input_required | approval_required
```

展示状态由后端按以下优先级派生：

```text
stopped                             -> stopped
input_required / approval_required -> waiting
failed                              -> error
executing                           -> working
succeeded                           -> done
running + idle                      -> idle
```

规则如下：

- 普通工具调用失败不代表整个任务失败；只有当前 Turn 以未处理错误结束才进入 `failed`。
- 历史事件不能覆盖新 Turn 的状态。
- 正常结束和异常结束必须优先使用结构化事件，不使用回复正文中的“error”“成功”等词汇判定。
- 进程不存在时始终显示 `stopped`，过期的等待或结果事件不能覆盖该状态。
- `done` 默认突出 8 秒，`error` 默认突出 15 秒；随后进程仍在且没有新 Turn 时，展示状态进入 `idle`，结果事件保留在通知和历史中。
- 每次状态变化携带 `agent_id`、`session_id`、`turn_id`、事件时间、数据来源和可信度。

数据可信度从高到低为：Hook 或官方结构化事件、会话文件结构化事件、进程和文件活动信息、文本提示。文本提示只能生成诊断提示，不能改变正式任务结果。

## 6. 会话注册表与事件流

所有数据源先转换为统一事件：

```text
进程 / Hook / 日志文件
          -> AgentAdapter
          -> DomainEvent
          -> SessionRegistry
          -> StatusEngine
          -> AgentViewSnapshot
          -> 前端
```

会话记录至少包含：

```text
agent_id
session_id
project_path
process_ids
turn_id
started_at
last_event_at
source
confidence
lifecycle
```

绑定策略：

1. Claude Hook 提供明确 `session_id` 时直接绑定。
2. 缺少明确 ID 时，只有“Agent 类型和规范化工作目录相同、日志最后事件不早于进程启动前 5 秒、且候选唯一”才接受关联，并标记为 `probable`。
3. 多个候选、缺少工作目录或时间证据不足时返回 `SessionAmbiguous`，不选择候选。
4. 适配器负责原始格式解析；会话注册表不包含 Claude/Codex 特有字段。

## 7. 后端架构

保持 Tauri 2 + Rust，重构为模块化单体：

```text
src-tauri/src/
├── domain/
│   ├── agent.rs
│   ├── session.rs
│   ├── event.rs
│   └── status.rs
├── application/
│   ├── session_registry.rs
│   ├── status_engine.rs
│   └── agent_service.rs
├── adapters/
│   ├── claude/
│   ├── codex/
│   ├── opencode/
│   └── hermes/
├── platform/
│   └── windows/
├── infrastructure/
│   ├── filesystem.rs
│   ├── process.rs
│   └── persistence.rs
└── interface/
    └── tauri_commands.rs
```

边界要求：

- `domain` 不依赖 Tauri、Win32、文件系统或具体 Agent 格式。
- `adapters` 只把外部格式转换为领域事件。
- `application` 负责会话绑定、状态计算和用例编排。
- `platform/windows` 实现打开路径、终端控制、进程终止、窗口聚焦、自启和快捷键。
- `interface` 提供版本化的前端协议，不包含业务判断。

## 8. 前端技术与架构

前端渐进迁移到 Svelte + TypeScript，保留 Vite、CSS 和 Tauri。迁移不是一次性重写。

```text
src/
├── bridge/
├── models/
├── stores/
├── components/
│   ├── island/
│   ├── cards/
│   ├── notifications/
│   ├── approvals/
│   └── controls/
├── layout/
├── themes/
└── windows/
    ├── island/
    └── overview/
```

### 8.1 前后端协调

- `bridge` 是前端唯一允许调用 Tauri API 的位置。
- 后端提供不可变、带协议版本的 `AgentViewSnapshot`。
- 组件以 `agent_id + session_id + turn_id` 作为身份，不以数组下标作为业务身份。
- 轮询更新不得重置当前选择、滚动位置、输入内容或布局编辑状态。
- 用户正在拖拽、输入或处理审批时，新快照进入待合并队列，在安全时机应用。
- 前端不重复推断 Agent 业务状态。

### 8.2 布局

采用已确认的 B 方案“自适应模块岛”：

- 身份与状态、紧急审批、核心操作保持固定。
- 状态、用量、日志、会话信息等作为可配置卡片。
- 卡片支持排序、隐藏、恢复及紧凑、标准、宽版尺寸。
- 使用响应式网格槽位，不保存任意像素坐标，不允许重叠或越界。
- 小窗口自动切换为单列并按重要性折叠次要内容。
- 布局编辑使用明确编辑模式；拖拽不是唯一调整方式。
- 布局配置带 schema 版本，支持迁移、备份和恢复默认。
- 提供“极简”“监控”“调试”预设。
- 通知和审批位于独立事件层，不参与普通卡片排版。

### 8.3 视觉体系

默认采用已确认的 B 方案“石墨玻璃”：深色石墨基底、轻量玻璃层级、克制蓝色强调和有限状态光效。纯黑硬件感保留为主题预设。

颜色、字体、间距、圆角、阴影、模糊、层级和动画曲线全部由设计令牌提供。组件不得硬编码主题值。动画必须尊重 `prefers-reduced-motion`，持续刷新不得触发无意义的入场动画。

## 9. 错误处理与诊断

- 每个 Agent 适配器独立失败，单个适配器不能拖垮应用。
- 内部错误使用结构化类型，例如 `LogUnavailable`、`ParseFailed`、`SessionAmbiguous`、`ProcessGone` 和 `PermissionDenied`。
- 数据同时携带新鲜度、来源和可信度，区分空数据、未知和读取失败。
- 读取失败时可保留最后一次确认快照，但必须标记过期，且不得继续产生实时状态通知。
- 单条损坏 JSON 被跳过并计数；连续或大面积解析失败会关闭该适配器的状态推断并显示诊断状态。
- 操作命令返回明确结果和可重试性。
- 日志记录适配器、会话 ID、事件类型和错误代码，不记录完整提示词、密钥或不必要的敏感路径。
- 本地诊断页支持导出脱敏报告。
- 单个前端卡片异常时只降级该卡片，布局配置损坏时恢复默认并保留备份。

## 10. 测试策略

### 10.1 后端

- 使用真实格式的脱敏 Claude/Codex 样本测试适配器。
- 单元测试覆盖事件标准化、会话匹配、状态优先级、过期规则和错误降级。
- 集成测试覆盖多 Agent、多项目、同目录多会话、日志轮转、半行 JSON 和进程消失。
- 每个已发现缺陷必须先有失败测试，再实现修复。

### 10.2 前端

- 使用 Vitest Browser Mode + Playwright 进行组件和交互测试。
- 覆盖轮询刷新不打断输入、会话切换一致性、拖拽排序、布局恢复和响应式降级。
- 对紧凑态、展开态、通知、审批、三种布局预设和主题建立截图回归。
- 测试高 DPI、多显示器、小屏、长文本和持续日志更新。

### 10.3 质量门禁

- Rust 单元与集成测试通过。
- TypeScript 类型检查和前端测试通过。
- Vite 生产构建与 Tauri 构建通过。
- Windows 安装包完成启动、托盘、自启、快捷键和卸载冒烟测试。
- 核心人工场景通过，截图不存在未审批变化。

## 11. 实施阶段

### 阶段 1：建立基线

完善忽略规则和敏感信息检查，确认现有 Git 历史和 v1.8.2 标签可回退，记录构建结果和已知错误。

### 阶段 2：建立正确性测试

加入脱敏样本，复现串会话、历史错误污染、日志倒序和状态不一致。此阶段不改变产品界面。

### 阶段 3：后端重构和修复

实现领域事件、会话注册表、多维状态引擎和 Agent 适配器，并保持旧前端接口兼容。完成真实场景联调后才进入前端迁移。

### 阶段 4：渐进迁移前端

建立 TypeScript 类型、Bridge 和 Store，依次迁移状态、日志、通知、审批、操作和总览组件。旧实现保留到新组件行为验证完成。

### 阶段 5：布局、视觉与发布门禁

落地自适应模块岛、石墨玻璃主题、布局编辑和预设，完成截图回归、高 DPI、多显示器和安装包验证后移除旧前端。

每个阶段单独提交。功能修复和视觉调整不得混在同一提交中。

## 12. 成功标准

- 活动会话不会显示其他项目或历史会话的内容。
- 无法确认归属时界面明确显示未知，而不是猜测。
- 历史错误不影响当前任务，工具失败被修复后不会误报任务失败。
- 状态、日志、目录和文件始终属于同一会话。
- 数据刷新期间用户操作和动画保持稳定。
- 用户可以安全地重排、隐藏和恢复卡片。
- 默认石墨玻璃主题在常见 Windows DPI、显示器和背景下保持清晰一致。
- 核心逻辑不依赖 Tauri 或 Win32，前端只依赖版本化 Bridge。
- 所有已知缺陷都有自动化回归测试。

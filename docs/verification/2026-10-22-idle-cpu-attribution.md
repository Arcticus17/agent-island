# 空闲 CPU 归因：诊断轮询按需加载（9.3% → 7.0%）

日期：2026-10-22
范围：`src/app/App.svelte`、`tests/browser/island-actions.test.ts`

## 先做归因，再动手

上一轮把轮询从 1.5s 降到 4.5s，空闲 CPU 只从 9.06% 降到 6.88%，说明大头不在扫描。
这轮先做了个对照实验：**把轮询临时关掉**（`effectivePollMs = 0`）重启再测：

| 配置 | 单核占用 |
| --- | --- |
| 基线（4.5s 轮询 + 每轮诊断） | **9.3%** |
| 关掉全部轮询 | **6.4%** |
| 4.5s 轮询、去掉每轮诊断刷新 | **7.0%** |

结论：轮询整体约 2.9 个百分点，其中**大半是"每轮额外再打一次诊断 IPC"**，而不是快照扫描本身。
关掉轮询后仍剩 6.4% —— 这是空闲 WebView（透明置顶窗口）的固有成本，属于另一个量级的问题。

## 改动：诊断按需加载

原来 `refreshAll()` 每轮都调用 `loadDiagnostics()`，等于一次轮询打两次 IPC，其中诊断的负载还不小。
现在：

- **首轮取一次**（摘要徽标需要这个数字）；
- 之后**只有抽屉展开时**才跟着轮询刷新；
- 展开抽屉的瞬间立刻补一次（`ontoggle`）；
- 命令执行后的刷新保持原样（用户刚操作完，数据要新）。

## 测试契约也随之更新

`keeps diagnostics polling single-flight…` 断言的是旧行为（收起状态也持续轮询、靠单飞合并）。
改成新的契约：

```
收起状态：轮询在跑（snapshotCalls > 1），但诊断只请求过 1 次
         首个请求 resolve 后，仍只有 1 次
展开抽屉：立刻补一次 → 2 次，且并发请求仍然被单飞合并
```

## 顺带记住的两条经验

1. **测 CPU 必须重启应用**：HMR 后旧实例的定时器还在，一次测量得到过 40.5% 的假数字。
2. 归因实验要用"关掉一块、测差值"的方式，别靠猜——这次直接推翻了我原以为的"扫描是大头"。

## 下一步

剩下 6.4% 是透明置顶窗口的空闲合成成本。可行的方向：
窗口隐藏时把 WebView 内容 `display: none`（减少合成层）、或改用系统级"点击穿透 + 热点"模型。
这属于架构级改动，应该单独评估，不宜夹在功能回合里做。
